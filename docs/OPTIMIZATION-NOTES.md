## 0. 前提

- 瓶颈不一定在 C++ 几何/栅格化；PDFium 每帧更新 90 个字段也可能是主瓶颈。
- 先用 S1/S2 拿到真实数据，再决定把精力放在 JS、字段更新还是 C++ 栅格化。

## 1. 值得优先落实的优化

1. **行级 dirty check**：只对 `rows[r]` 发生变化的行写 `F[r].value`。
   `ARCHITECTURE.md §4.2` 已经要求；正式实现必须内建，不作为后期补丁。
2. **TileShape 几何缓存**：以 `TileShape::keyForTile()` 的 key 为索引，
   `buildShape/expand/indexTable` 每种几何只做一次；`runtime` 的 `shapeId` 直接复用。
3. **三角形包围盒裁剪**：只遍历三角形 bbox 与 160×90 网格的交集；
   保留原有边函数与边界判定；保留一份参考实现，随机三角形逐格对拍。
4. **runtime 每实例预计算 sin/cos**：每个砖实例只算一次旋转系数，供全部顶点复用；
   C++ 与 JS 必须使用同一变换顺序；用 `frames` / `runtime` 的网格差异测试验证。
5. **运行时缓存**：形状表启动解码一次；90 个字段引用一次获取；
   预生成 `CH[10][W+1]`；复用同尺寸缓冲；只解码当前帧；`k === idx` 不重绘。

## 2. 两种模式的选择

- **frames 先实现并作为默认**；runtime 保留设计，等 S5 实测后再决定是否作默认。
- 两种模式最终都要更新同样的 90 个字段；如果字段更新是瓶颈，runtime 不能解决。
- 不建议为了“看起来更先进”提前切换 runtime。

## 3. 明确不采用

- WebGL / WebGPU、canvas 画布、用 PDF.js 替换原生 PDFium。
- 每个字符单独建字段、位图替代字符网格（破坏 90 行字段/字符网格契约）。
- `setInterval`、每帧 `seek()`、无上限提升 fps、引入新的 pip/npm 依赖。

## 6. S1/S2 实测后的修订（2026-11-13）

数据源：`SPIKES.md` 的 S1/S2 结论（90 行 Courier 20.08 ms / 49.8 fps / setter 7.59 ms）。

### 6.1 站得住、且优先级要提的

- **`CH[10][W+1]` 预生成 + 字段引用一次性获取**：这是 §1 里最值钱的一条。
  setter 段 7.59 ms 装的就是 90×160 字符的字符串拼装与赋值，全部可省。
- **行级 dirty check**：保留，但下调预期——满场更新也才 7.6 ms，而镜头一动几乎每行都变，
  跳过率不会高。它的价值在静止段与 HUD 节流，不在平均帧。
- **frames 优先**：数据直接支撑（49.8 vs Type3 14.7，而 runtime 还要在这之上再叠一层 JS 栅格化）。

### 6.2 要降级的

- §1.2–1.4 的 C++ 热路径（形状缓存 / 可见砖裁剪 / 三角形 bbox 裁剪）与 `runtime` 的 sin/cos 预计算，
  **对 frames 帧率没有贡献**；只影响构建耗时与 runtime 开销。已按此改 §4 的顺序，不再单列阶段。
- §0 的判断只对了一半：瓶颈确实在 PDFium 一侧，但不在 JS setter（38%），
  而在**字段重绘（62%，约 12.5 ms）**——这部分任何 C++/JS 改动都碰不到。
  因此整份清单的收益上限是 `33.3 − 12.5 ≈ 20 ms`，别指望"优化完能上 60 fps"。

### 6.3 实测新增的三个数

| 结论 | 数 | 用法 |
|---|---|---|
| 全行更新成本模型 | ≈ 0.17 ms/行（setter 0.084 + 重绘 ~0.087）+ 固定 ~5 ms | 30 fps 下行数上限约 160 行；135 行已近极限、180 行超限，与实测吻合 |
| runtime 模式的 JS 预算 | 33.3 − 12.5 − 7.6 ≈ **13 ms** | 要装下三角形栅格化 + 90 行字符串构建；60 fps 为负数，直接排除 |
| 灰度不是精确值 | PDFium 对文字做亚像素 AA，`SPEC.md §5` 的 10 级灰度只是设计意图 | 验收口径改为"密度单调可辨"，不为 2×2 覆盖/精确密度投入 |
