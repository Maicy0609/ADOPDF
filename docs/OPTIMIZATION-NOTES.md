# 外部优化建议（摘录，2026-11-12）

> 来源：外部 AI 对 ADOPDF 的 review。**仅作参考，不是决策**；
> 与 `DECISIONS.md` / `SPEC.md` / `ARCHITECTURE.md` 冲突时，以后者为准。
>
> 当前状态：S1/S2 未通过，正式生成器未开始。不要跳过 S1/S2 直接写优化后的渲染器。

## 0. 前提

- 瓶颈不一定在 C++ 几何/栅格化；PDFium 每帧更新 90 个字段也可能是主瓶颈。
- 先用 S1/S2 拿到真实数据，再决定把精力放在 JS、字段更新还是 C++ 栅格化。

## 1. 值得优先落实的优化

1. **行级 dirty check**：只对 `rows[r]` 发生变化的行写 `F[r].value`。
   `ARCHITECTURE.md §4.2` 已经要求；正式实现必须内建，不作为后期补丁。
2. **TileShape 几何缓存**：以 `TileShape::keyForTile()` 的 key 为索引，
   `buildShape/expand/indexTable` 每种几何只做一次；`runtime` 的 `shapeId` 直接复用。
3. **三角形包围盒裁剪**：只遍历三角形 bbox 与 160×90 网格的交集；
   保留原有边函数与边界判定；保留一份参考实现，随机三角形逐格对拍。
4. **runtime 每实例预计算 sin/cos**：每个砖实例只算一次旋转系数，供全部顶点复用；
   C++ 与 JS 必须使用同一变换顺序；用 `frames` / `runtime` 的网格差异测试验证。
5. **运行时缓存**：形状表启动解码一次；90 个字段引用一次获取；
   预生成 `CH[10][W+1]`；复用同尺寸缓冲；只解码当前帧；`k === idx` 不重绘。

## 2. 两种模式的选择

- **frames 先实现并作为默认**；runtime 保留设计，等 S5 实测后再决定是否作默认。
- 两种模式最终都要更新同样的 90 个字段；如果字段更新是瓶颈，runtime 不能解决。
- 不建议为了“看起来更先进”提前切换 runtime。

## 3. 明确不采用

- WebGL / WebGPU、canvas 画布、用 PDF.js 替换原生 PDFium。
- 每个字符单独建字段、位图替代字符网格（破坏 90 行字段/字符网格契约）。
- `setInterval`、每帧 `seek()`、无上限提升 fps、引入新的 pip/npm 依赖。

## 4. 建议实施顺序

1. 完成 S1/S2 的 Chrome 实测。
2. 实现 frames 正式生成器（dirty rows / 字段引用 / 字符缓存内建）。
3. C++ 热路径：Shape Cache → 可见砖裁剪 → 三角形 bbox 裁剪（每项都要对拍）。
4. 实现 runtime 模式，复用几何结果与形状表。
5. 执行 S3/S5，比较 fps / PDF 体积 / 初始化时间 / 视觉，确定默认模式。
